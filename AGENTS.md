# AGENTS.md

This file guides AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository.

## Overview

**Paper Plane** ("Send it flying."), a real-time chat app in Python (Flask). The repo is `chat_app` and the Python package is `paperplane`. People sign up, start direct messages and group chats, and see messages, unread counts and who is online the moment things change. The plan is `docs/PLAN.md`.

It is a learning project for **WebSockets, event handling and authorization**, so those parts stay easy to read: short comments that explain *why*, plain WebSockets (`flask-sock` on the server, the browser's own `WebSocket`; no Socket.IO), an event protocol written by hand, login written by hand (no Flask-Login), and no extra libraries unless the owner asks for them. Write the README in simple (A1-level) English.

Python 3.13 is at `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`. Use the virtual environment:

- Install: `.venv\Scripts\python -m pip install -r requirements.txt` (create `.venv` with `python -m venv .venv` first if it's missing).
- First time: `.venv\Scripts\flask --app paperplane upgrade-db` (makes the tables). Then open the site and sign up, or click Try the demo.
- Run: `.venv\Scripts\flask --app paperplane run --debug --port 5015`, then open http://127.0.0.1:5015. (Ports: Swap Meter 5000, Ambon Alert 5001, Ang Gastos! 5002, Sangkap 5003, Gawi 5004, Akda 5005, Hire Wire 5006, Plan-It 5007, ShiroMoto 5008, DFJC 5009, Ticket Tock 5010, Tally Ho! 5011, J: Drive 5012, Right On Cue 5013, Pulse Check 5014.)
- Test: `.venv\Scripts\python -m pytest`. Every test gets a fresh SQLite file and never uses the internet. `tests/test_live.py` starts the real app on a free 127.0.0.1 port (`live_helpers.Server`) and connects real WebSocket clients (`BrowserLikeClient`: simple-websocket's client leaves the port out of `Host`, browsers don't, and the Origin check compares them); a refused handshake raises `live_helpers.Refused`. Set `TEST_DATABASE_URL` to an **empty** PostgreSQL database to run the same tests there (each test drops and remakes the tables). SQLAlchemy warnings fail the tests (`pytest.ini`).
- Other commands: `set-password <username>`, `purge-demos`.

## Architecture

- **The login cookie is `paperplane_session`, not Flask's `session`:** browsers keep cookies per host, not per port, so the owner's other Flask apps on 127.0.0.1 would overwrite it (`tests/test_auth.py::test_another_local_apps_cookie_doesnt_log_you_out`).
- **Accounts (`auth.py`):** open sign-up with a username (3-20 small letters, numbers or `_`, starting with a letter; a few names like `admin` are reserved) and a password. There is no email, so a forgotten password is recovered with a **recovery code** (`XXXX-XXXX-XXXX`), shown once at sign-up (rendered straight into the response, never put in a cookie) and stored only as a hash; using it, or Settings' "New recovery code", makes a new one. Hashes from Werkzeug; 5 wrong passwords (or codes) lock the account for 15 minutes, one address may try 30 logins per 15 minutes and make 5 accounts an hour (`limits.py`). `user_from_session()` checks `session_version` (a password change or "Log out other devices" logs out every other cookie) and a demo's expiry; `load_user()` uses it on every request and puts `g.user` on the request.
- **Demo (`seed.py`, `views/demo.py`):** Try Demo makes a `DemoTeam` ("Papel Studio") with the visitor, Mika Santos (`is_bot` False), and four made-up teammates (Ana, Ben, Carlo, Dana; `is_bot` True). Demo usernames are `d<team>.<name>` (a dot can't be typed into a real username), shown as `@<name>` (`User.handle`). Nobody can log in to a demo person with a password. Demo people start with a random `session_version`, can't change their account, and are deleted with their team after 24 hours (`seed.purge`, also on every Try Demo click and by `purge-demos`). `demo_teams` and `users` use `sqlite_autoincrement`, so a deleted demo's ids are never handed out again. At most 20 demos at once, 10 per network an hour (not with `--debug`). **Every page the demo can open must show an example, so add sample data with every new feature** (`seed.fillers`; `tests/test_demo.py::test_every_page_of_the_demo_shows_an_example`). The sample chats (`seed.sample_chats`) are written straight into the tables with `add_chat` / `say` (numbered by `chats.bump`): the "Papel Studio" group (owned by Ana), DMs with Ana, Ben and Carlo, "Weekend Hike" (Ben's) and "Launch Plans" (Mika's), with 5 messages Mika hasn't read yet. The sample stories are in `seed.sample_stories` (see Stories).
- **Authorization (`access.py`), the authorization lesson, read it first:** every rule about chats is in ONE place, and pages and WebSocket events both ask it. Two questions in order: `load(s, user, chat_id)` gives (chat, your membership) or raises `NotFound`. A chat you aren't in, were removed from, or that was deleted is "not found", never "forbidden", so a stranger can't learn that chat 41 exists. Then `can(action, chat, membership, target=None, muted=False, blocked=False)` / `require(...)` look the action up in `GROUP_RULES` (owner / admin / member) or `DM_RULES` (both people can only read, send, react, edit and delete their own). Actions done TO someone (`TARGETED`: remove, mute, change roles) need a higher role than the target and never act on yourself. Muted people and DMs with a block lose `SPEAKING` actions. `same_world(a, b)`: real people only meet real people, and a demo person only their own team. `tests/test_access.py` walks the whole table for every role, written out by hand: change both on purpose.
- **Problems (`problems.py`):** the domain code raises `NotFound` (404), `Forbidden` (403), `Invalid` (400), `TooMany` (429), `Conflict` (409), each with a plain message. Pages show them (`views/chats.py` registers an error handler; forms catch `Invalid` and show it); the event router turns them into `{"type": "error", "code": ...}`.
- **Chats (`chats.py`):** the domain functions pages and events share: `start_dm` (one DM per pair: `conversations.dm_key` "small id:big id" is UNIQUE, and a savepoint catches two people starting it at once), `create_group` (you are the owner), `send_message`, `post_system`, `mark_read`, `chat_list`, `messages_page`, `changes_since`, `find_person`, `people_i_know`. They check the rules, change the tables, `emit()` live events, and leave the commit to the caller. **Order and unread:** `bump()` takes the chat's next `last_seq` (and `version`) with one `UPDATE ... RETURNING` inside the transaction, so two messages can never share a seq; `memberships.last_read_seq` says how far you've read, so unread = `last_seq - last_read_seq` with no counting query (sending sets your own pointer to your message; `mark_read` never goes backwards). **Sending twice is safe:** every message has a `client_id` (the browser's UUID, or one the page puts in the form), `UNIQUE(sender_id, client_id)`, so a re-sent message is saved once and the first copy comes back. **History:** `visible_from()`: a group with `history_visible` off shows a member only messages after their `joined_seq`, in pages and catch-up alike. Hooks for later stages: `after_send_hooks`, `speaking_checks`.
- **Live events wait for the commit (`outbox.py`):** `emit(s, user_ids, type, data)` only holds the event on the session; SQLAlchemy's `after_commit` hook hands it to the hub (stage 3), and `after_rollback` throws it away, so nobody sees a message that was never saved. A message event carries its facts AND its HTML (`message_data()`, drawn once from `_message_live.html`, the same macro as the page, so live and reloaded messages look the same; the browser adds `mine` to its own). `render_fragment()` draws a template outside a page (a WebSocket thread, the demo crew).
- **The WebSocket endpoint (`live.py`), the WebSocket lesson:** `/ws` (flask-sock). The HANDSHAKE is an HTTP request checked before it is upgraded (`check_handshake`, an `app.before_request` registered AFTER the blueprints, so `auth.load_user` has run): it must be a WebSocket upgrade (400), its **`Origin` header must be this site** (`request.scheme://request.host`, or `ALLOWED_ORIGINS`; 403), because browsers send cookies with a cross-site WebSocket handshake and a CSRF token can't go with it (cross-site WebSocket hijacking), and the login cookie must be valid (401). Then `serve()` closes the request's database session (a socket may stay open for hours and must not hold a pool connection; each event opens its own), registers a `Connection`, sends `hello`, and loops: each text frame goes to `events.dispatch()`, the answers go back on the same socket. Staying alive: simple-websocket sends protocol pings every 25 s (`SOCK_SERVER_OPTIONS`, with `max_message_size` 16 KB), the browser sends `{"type": "ping"}` every 25 s (a page can't see protocol pings), and a socket silent for 70 s is closed. `/me.json` tells a page that can't connect whether it is still logged in.
- **The hub (`hub.py`):** who is connected, in this process's memory: `by_user[user_id] = {Connection, ...}` (one per tab, at most 5 per person, close code 4008 for a sixth). `publish(user_ids, payload)` makes the JSON once and sends it to every tab of those people; a socket that fails to send is forgotten (`unregister` is safe twice). Each `Connection` has its own lock so two threads never write into one socket at once. `close_user()` sends `bye` and closes with **4001** (Settings calls it after a password change or "Log out other devices", via `views/settings.close_sockets`; the browser reloads on 4001). `allow(key, limit, seconds)` is a sliding-window rate limit in memory. Hooks: `on_connect`, `on_disconnect` (presence). **Why ONE server process:** the hub is in memory, so a message saved in process A would never reach a tab connected to process B. `publish()` is the one place to change to grow past one process (PostgreSQL `LISTEN/NOTIFY` or Redis): explained in the README, not built.
- **The event protocol and router (`events.py`, `live_events.py`), the event-handling lesson:** every frame is one JSON object. Browser to server: `{"type", "ref", "data"}` (`ref` is the browser's own number for the request); server to browser: `{"type": "ack", "ref", "data"}`, `{"type": "error", "ref", "code", "message"}`, or news without a ref (`message.new`, `read`, `unread.total`, `conversation.new`, `bye`, `hello`, `pong`). Handlers are registered with `@on("type", limit=(n, seconds), field=(type, required, max_length))`. `dispatch()` does the same steps for every frame: read the JSON and the envelope, find the handler, check the data's SHAPE (`check_shape`: refuses `true` for an int, too-long text...), open a session and check the person is still logged in with the socket's `session_version` (else close 4001 and answer `logged_out`), check the rate limit, run the handler (which checks PERMISSION through the domain code), commit (the others' events go out now) and ack, or roll back and answer the problem's code. A crash answers `server_error` without details. Handlers: `message.send` (20 per 10 s; the ack carries the saved message, also when it was a duplicate), `read`, `sync` (after a reconnect: the whole chat list's HTML, the menu total, and the open chat's messages changed since the version the tab has, or `reload` past `CATCH_UP_LIMIT`, or `gone`). Handlers take data and return data, so `tests/test_events.py` runs them with fake sockets.
- **The browser side (`static/socket.js`, `static/chat.js`), loaded on every logged-in page:** `Live.request(type, data)` gives a Promise for the ack or error, matched by `ref`; a request made while offline waits and is sent when the socket opens again (safe, because every request can be repeated). `Live.tell()` sends without an answer. Heartbeat: a ping every 25 s; no pong in 10 s means a dead connection, so close and reconnect. Reconnect waits 1, 2, 4 ... 30 s, each a random amount between half and all of it (jitter), shows "Reconnecting..." only after 2 s, and asks `/me.json` after 3 tries. After a reconnect, `chat.js` calls `sync`. `chat.js`: sending draws a "Sending..." bubble from text (never HTML), the server's `message.new` (matched by `client_id`) or the ack replaces it with the saved copy; a failed send says "Not sent. Tap to try again." with the same `client_id`. New messages are drawn from the HTML the server sent, marked `mine`, joined to the run before them, and get a day line when the day changes. The list row moves to the top with its preview and time; badges, the menu's total and the tab's title (`(3) Chats - Paper Plane`) change live; the open chat is marked read while the tab is visible and scrolled to the bottom. Enter sends, Shift+Enter makes a new line.
- **Presence (`presence.py`):** worked out from the hub's open sockets, never stored except `users.last_seen_at`. Online = at least one tab, and one is in front (or was hidden less than `AWAY_AFTER`, 5 minutes); Away = every tab hidden for 5 minutes (the browser sends `presence {visible}` on `visibilitychange`); Offline = no tab, but only after `GRACE` (10 s), so a page reload never flickers. `Presence` hangs on the hub's `on_connect` / `on_disconnect` hooks; a ticker thread (not in tests: they call `tick(now)` with a pretend clock) makes the grace and away times happen every 2 s. A change is announced (`presence {user_id, status, last_seen}`) only to `contacts()`: people who share an active chat (and stage 7 takes blocked people out, `audience_filters`), and never when the person turned off "Show when I'm online" (Settings, Privacy; turning it off sends everyone "offline" with no last seen, and pages show offline). After `hello`, a socket gets `presence.snapshot` (its contacts' statuses). Pages draw dots with `presence_of(person)` and the DM header's line with `presence_words(person)` (Online / Away / Last seen 5 min ago / @handle).
- **Typing (`live_events.typing`):** `typing {conversation_id}` checks you may send there (`require_speaking`), then goes to the chat's other members only (never stored, never to the typer); the browser sends it at most every 3 s and the server drops anything within 2 s (`hub.allow`). The browser shows "Ana is typing...", "Ana and Ben are typing...", "Several people are typing..." for 5 s, and clears a person's when their message arrives.
- **The demo crew (`crew.py`):** while a demo has a REAL tab open, a thread (every 0.5 s; tests call `step(now)` with `crew.seed` for repeatable choices) plays the made-up teammates through the real code paths: they come online by registering a `BotConnection` (a pretend socket, `played = True`) in the hub, so presence announces them like anyone; they read (`chats.mark_read`), type (the same `typing` event) and send (`chats.send_message`), so every event goes through the outbox. `SCRIPT`: Ana and Ben come online at once, Carlo after 14 s and says a line at 22 s, Ben looks away at 40 s (Away 5 minutes later), Ana asks something at 75 s, Dana comes in at 120 s (her "last seen" is 2 hours ago until then). Replies: `chats.after_send_hooks` calls `notice()` for a real person's message in a demo chat (a session marked `s.info["crew"]` is the crew itself, so it never answers itself); a teammate in that chat comes online if needed, reads it ("Seen"), types, and answers after 5-7.5 s with `reply_for()` (topics first, then greetings, then questions, then a fallback); one reply on its way per chat. A minute after the last real tab closes, the teammates go offline and the demo goes quiet (no work, no database calls). **Friend links (`views/demo.py`):** the visitor's `/demo/friends` (linked from the Demo tag) has a signed link per teammate (`tokens.make("friend", team, user)`), valid while the demo lasts. Opening it only SHOWS a Join page (chat apps open links for previews); the button logs that browser in as the teammate. The crew stops playing anyone with a real socket (`has_real_tab`), so two real people chat live (open it in a private window or on a phone).
- **Message tools (`tools.py`, `views/messages.py`, the `message.edit` / `message.delete` / `message.react` events):** every change takes the chat's next version (`chats.bump`), stamps the message with it, and emits `message.updated` with the message drawn again (tabs replace it; a tab that was away gets it from `sync`). `load_message()` checks you can see the chat AND the message (not before your `joined_seq` in a group that hides history). **Edit**: your own text messages, for 24 hours (`EDIT_WINDOW`), shows "edited". **Delete for everyone**: your own (`delete_own`), or anyone's in a group you own or run (`delete_any`); the words are ERASED (`body = ""`), the reactions removed, the row and seq kept ("Message deleted"); deleting twice is fine. **Reactions**: one of `EMOJI` (6), pressing again takes it back (`UNIQUE(message_id, user_id, emoji)`); muted people can't (`require_speaking("react")`). **Replies**: `messages.reply_to_id`, only to a message in the same chat that you can see (`reply_target`); a reply to a deleted message quotes "Message deleted". `prepare(s, messages)` puts `reaction_list` and `reply_info` on messages for the template in two queries. **Seen by** (`readers`, `seen_words`): under the chat's last message when it is yours: "Seen" in a DM, "Seen by Ana and Ben", "Seen by everyone"; the page gives the browser every member's `last_read_seq` (`data-readers`), and `read` events keep it live. Without JavaScript: the ⋯ menu is a `<details>` with forms (react, delete with the themed confirm) and links (`?reply=<id>` shows a reply banner; `/messages/<id>/edit`). **A live message's HTML never carries a CSRF token** (it is drawn once and sent to everyone: it would be the sender's token); `chat.js` adds the reader's own from `<meta name="csrf-token">`. CSS shows Edit only on your messages and Delete on yours, or on all for a group's owner and admins (`data-role` on the chat).
- **Running a group (`groups.py`, `views/groups.py`, `group_info.html`):** rename, add people (a returning member is the same row brought back; new and returning members start "read up to now", and `joined_seq` is where the history rule starts for them), remove (only someone of a LOWER role), change roles (owner only, admin/member), hand over (the owner becomes an admin), mute for 1 / 8 / 24 hours (`memberships.muted_until`; `groups.mute_flags` is a `chats.speaking_checks` hook: a muted member can read but not send or react, and the composer says until when), leave (an owner's group passes to the longest-serving admin, else member; the last one out deletes it), delete (owner; `deleted_at`, so `access.load` says not found), and "New members see earlier messages" (`history_visible`). Each action leaves a system line ("Ana added Ben", `chats.post_system`) and tells tabs live: `conversation.updated` (a new name, everyone), `conversation.new` (you were added), `conversation.removed` (you were removed, left, or it was deleted: the row leaves your list, an open chat says why and goes to Chats), `membership.updated` (your role or mute changed, or a block opened or closed your DM: the open chat reloads). A removed person hears nothing more at once: events go to CURRENT members only, and every event they send is checked again. The info page (`/chats/<id>/info`) shows only the controls your role allows (`can()` with the member as target); a DM's info page has Block. Forms come back to the info page with a toast (`act()`); a 404 problem stays a 404.
- **Invite links (`groups.create_invite` / `join`, `/join/<code>`):** a random code (not signed, so turning it off ends it), works for 1 day / 7 days / always and once / 10 times / any number (`INVITE_EXPIRY`, `INVITE_USES`), at most 10 working links per group, managers only. The join page needs a login and only SHOWS the group; the button joins. Using it counts with one guarded `UPDATE ... WHERE uses < max_uses`, so two people can't both take the last place; joining twice is fine; a demo's link only works inside that demo and a real group's only for real people.
- **Blocking (`blocks.py`):** one row per (blocker, blocked). It works both ways for talking: in their DM neither can send or react (`dm_flags`, a `chats.speaking_checks` hook; the composer says why), neither can start a new DM (`check_can_start`) or add the other to a group (`create_group`, `add_people`), and neither sees the other online (`presence.audience_filters` and `presence.status_for_page`, which caches `hidden_ids` per page). Blocking doesn't throw anyone out of a shared group, and the blocked person isn't told. Settings lists blocked people with Unblock. Block/unblock redirect only inside the site (`auth.safe_next`).
- **Pictures and files (`files.py`, `views/files.py`):** big things don't travel over the WebSocket: a file goes up with the composer's normal multipart form (`/chats/<id>/send`; `chat.js` sends the same form with `fetch` and gets JSON back), and the message pointing to it is saved in the same transaction (`chats.send_message(..., upload=files.prepare(...))`; the words may then be empty). `prepare()` checks: at most 5 MB (`MAX_CONTENT_LENGTH` 6 MB), pictures (JPEG, PNG, GIF, WebP) are opened by Pillow and saved AGAIN as WebP by us (turned the right way up with `exif_transpose`, then without EXIF, so no GPS position; at most 1600 px plus a 480 px thumbnail; `MAX_IMAGE_PIXELS` 40 M and the bomb WARNING turned into a refusal); other files only by name (PDF, txt, csv, md, docx, xlsx, pptx, zip; `FILE_TYPES` sets the type, never the browser) and kept as they are. Names go through `secure_filename`. Space: 50 MB per person, 10 MB per demo (`check_room`, `TooMany`). Stored in the database (`attachments.data` / `thumb`, `deferred` so lists never load bytes). `/files/<id>` and `/files/<id>/thumb` serve only to people who may see the message (`load_for`: `access.load` plus the history rule; a deleted message deletes its files); pictures inline, everything else `attachment`, always with a `sandbox` CSP, nosniff, and `Cache-Control: private`. The list says "Photo" or the file's name for a message without words.
- **Link previews (`previews.py`):** the SERVER fetches someone else's page, so it carries Pulse Check's private-network guard (SSRF): `url_problem()` (http(s), a name, no password, no `localhost` / `.internal` names, no private literal addresses), then `fetch()` looks the name up ITSELF, keeps only public answers (`allowed_ip`: `is_global`, IPv4-mapped IPv6 unwrapped; never the metadata service 169.254.169.254) and connects to THAT address (DNS rebinding), checks every redirect again (at most 3), reads at most 256 KB of `text/html` in 5 s, sends no cookies. `read_page()` takes `og:title` / `<title>`, `og:description` / `description`, `og:site_name`. It runs in a 2-thread pool AFTER the commit (`outbox.after_commit`: never before, never after a rollback; `chats.after_send_hooks`), saves a `LinkPreview` (one per message) and sends `message.updated`. An edit drops the preview and looks again; a delete drops it. `PREVIEWS` is off in tests (they call `make_preview(app, id, fetcher=...)`); `ALLOW_PRIVATE_TARGETS` lets your own PC fetch 127.0.0.1 (refused on Render).
- **Find and notify (`notify.py`, `views/notify.py`):** **Search** (`/search?q=&chat=`) looks only in your own active chats, at messages you may read (not deleted, the history rule), case-insensitive, LIKE wildcards made plain (`like_pattern`), newest 50; results link to `/chats/<id>?before=<seq+20>#m-<id>` and mark the words (`snippet`, escaped). **Mentions**: `@handle` of a group member in a group message saves a `Mention` (`record_mentions`, an `after_send_hooks` step); the chat row shows a red @ until you read past it (`mention_counts`), `linkify` draws `@handles` as `.mention` (after escaping; `chat.js` marks yours `.is-me`), and typing `@` in a group suggests members (`data-people`). **Muting a chat** (`memberships.notify_off_until`, NOT `muted_until`, which an admin sets): 1 hour / 8 hours / until turned back on (`FOREVER`), from the bell in the chat header; a muted chat keeps a grey badge but stays out of the menu's number (`chats.counts_in_total`) and gets no notifications. **Who gets told** is decided on the server once (`after_message`): every member except the sender and those who muted it; someone with a tab open gets a `notify` event (the browser shows a Notification if that tab isn't on the chat, after "Turn on notifications" in Settings), someone with no tab gets a **web push** on each device (`push()` in a 2-thread pool after the commit; VAPID keys from `flask --app paperplane make-vapid-keys`; a 404/410 device is forgotten). `/notifications/devices` takes the browser's subscription (JSON + `X-CSRF-Token`; https endpoints only). **Installable app**: `static/site.webmanifest`, `/sw.js` (cache + offline page + push + notification click), icons drawn by `docs/make_icons.py` from the owner's logo (see the UI rules). Settings sections keep a fixed order (`SECTION_ORDER`).
- **Chat pages (`views/chats.py`):** `/chats` (the list), `/chats/<id>` (the list and the chat: the latest 50 messages, "Load earlier messages" by seq, opening it marks it read), `/chats/<id>/send` (a form POST with a `client_id` from the page, so a reloaded form never sends twice), `/chats/new` (Message Someone by username, People You Know, New Group). The menu's unread number comes from `unread_total()` on every page. The message list scrolls inside a `column-reverse` box, so it starts at the newest message without JavaScript. Message times use `thread()`: a day line between days, and a person's run of messages within 5 minutes shares one name and avatar (`follows`).
- **Times (`dates.py`, `formatting.py`):** the database holds naive UTC. Pages show the person's own time zone (Settings, Asia/Manila at first): `clock`, `day_label` (Today, Yesterday, a weekday, a date), `short_when`, `ago`. Live messages carry `<time datetime="...Z">` and the browser writes them in its own words. `linkify` escapes a message piece by piece and makes only `http(s)://` addresses into links (`target="_blank" rel="noopener noreferrer nofollow ugc"`).
- **Database:** SQLAlchemy 2.0 ORM (typed `Mapped[...]`), plain (not Flask-SQLAlchemy). `paperplane/db.py` makes one engine per app and one session per request: `db.session()`; code outside a request uses `db.new_session()` and closes it. Every session knows its app (`session.info["app"]`). SQLite locally (`instance/paperplane.sqlite`, WAL mode, a 30-second busy timeout, `check_same_thread=False` because every WebSocket runs in its own thread), PostgreSQL (**Neon**, psycopg 3) when `DATABASE_URL` is set.
- **Migrations: Alembic**, in `paperplane/migrations/`. `flask --app paperplane upgrade-db` runs them (with SQLite's foreign keys switched off during the run, so a table rebuild can't cascade-delete rows); Render runs it before gunicorn.
  - **To change the schema:** edit `models.py`, then `.venv\Scripts\alembic revision --autogenerate -m "what changed" --rev-id 000N`, **read the new file and fix it** (booleans default to `sa.true()` / `sa.false()`, never `sa.text('1')`, so PostgreSQL accepts them; a new NOT NULL column needs a `server_default`), and commit it. Never edit a migration that has run on the live site. `tests/test_migrations.py` fails if the models and the migrations disagree.
  - Every foreign key to a parent that is deleted in bulk (`ON DELETE CASCADE`) needs an index that STARTS with that column, or the cascade scans the whole table (`test_bulk_deleted_parents_have_an_index_for_each_child`).
- **Every page works without JavaScript.** `app.js` only adds extras. The CSP (`__init__.py`, built per request so `connect-src` can name `ws://` and `wss://` on this host) has no inline scripts or styles, so **never use `style=""` or inline `<script>`** (`tests/test_look.py` checks the templates).
- **Deploy:** `render.yaml` (service `paper-plane`, free plan, Singapore; `upgrade-db` then ONE gunicorn process, `gthread`, 64 threads: each WebSocket holds a thread, and the hub needs every socket in one process) + Neon (Singapore, the pooled connection string). Environment: `SECRET_KEY` (made by Render; never change it), `DATABASE_URL`, `BASE_URL`, and optionally `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`. `create_app` refuses to start on Render without `SECRET_KEY` or `DATABASE_URL`, or with `ALLOW_PRIVATE_TARGETS`. ## UI rules (the owner's priority is neatness)

- **Colours (PR #4): four palettes, pink by default.** The app is drawn in the person's colour: pink (the logo's, the default), purple, red or blue (`users.accent`, migration 0007; Settings > Appearance; `views/settings.ACCENTS`). It is saved on the ACCOUNT, and the server puts it on `<html data-accent="...">` (base.html, `accent()`), with the browser bar colour (`theme_colour()`), so the page is right from the first paint. In `style.css` each palette block (`:root[data-accent="purple"]` ...; pink is also plain `:root`) defines only `--pal-*` values, each in a light and a dark (`-d`) version (36 per palette: accent, hover, soft, link, bubble, fold, sky top/bottom/muted, day sky, page, soft, rule, row hover, border, muted, ink, and dark surfaces); the light `:root` block and the two dark blocks map the app's tokens to them (`--accent: var(--pal-accent)` / `var(--pal-accent-d)`), so there is no dark block per colour. `tests/test_look.py` checks every palette in light and dark for 4.5:1 text and 3:1 control borders. Choosing a colour in Appearance shows at once (`app.js setUpAccent`) and saves; light or dark stays per device. Danger, ok, presence and mention colours are the same in every palette.
- **Look: paper planes in the chosen colour's sky**, drawn in CSS and inline SVG: the sidebar is the SKY (`.sky`: a gradient of the colour with two flat cloud puffs below the menu; a night sky with small stars in dark mode), cards and message bubbles are white PAPER with a soft shadow, page titles have a dashed TRAIL under them (`.title-trail`), empty states show a little paper plane, and the logo is the owner's own picture. **The logo** (since PR #6; PR #2 had two chat bubbles): `docs/logo/paper-plane-logo.webp`, a pink paper plane with a dotted trail behind it, given on a white background. The owner wanted NO background: `docs/cut_out_logo.py` (Pillow, the app's own `.venv`) cuts it out into `docs/logo/paper-plane-logo.png` (a flood fill from the edges takes the white, so the plane's light stripe stays; specks of compression noise go too; the edge pixels keep the plane's colour with a matching opacity, so there is no white fringe). Shown with no tile: in the menu it has a thin soft white edge (`filter: drop-shadow`, never `box-shadow`, which would draw a box) so it stands out on the coloured sky. `docs/make_icons.py` (Playwright + Edge, borrowed: `..\expense_tracker\.venv\Scripts\python docs\make_icons.py`) draws from the PNG: `static/icons/logo.png` (256 px, shown by `logo(size)` in `_icons.html` in the menu and on the login), `icon-32/192/512.png` and `favicon.ico` (see-through), `apple-touch-icon.png` and `icon-maskable-512.png` (the plane at 72% inside Android's safe circle), also see-through: the owner wants no white background on the app icon either (an iPhone or Android launcher fills the see-through part with its own colour, often black). Run both after changing the picture, and change `CACHE` in `sw.js` so installed apps fetch the new icons. The app's default colour (pink) matches the logo. Buttons are round pills. Colours are tokens on `:root`, filled from the palette (above). Outfit for headings, Inter for text, self-hosted in `static/fonts/`. Dark mode ("night sky") is defined twice in `style.css` (device setting + the choice in Settings); change both blocks together (`tests/test_look.py` checks they match and checks the main text colours for 4.5:1). Avatars are a letter on one of 8 tones (`User.tone`, `.tone-1`..`.tone-8`, all white text 4.5:1).
- **Photos, Files and Links (PR #7; `media.py`, `views/groups.media_page`, `chat_media.html`, `_media_card.html`).** Every chat's history of what was sent: `/chats/<id>/media?tab=photos|files|links&before=` (tabs are plain links; with no tab, the first one with something in it opens), and a card on BOTH chat info pages (the latest 6 photos and the three numbers, `media.counts`). The rules are the chat's own: `access.load` (members now; strangers and people who left get 404), `chats.visible_from` (a group that hides history hides its media too) and `Message.deleted_at` (a deleted message's files are already deleted by `files.forget`; its links leave too). Photos and Files are `attachments` (kind `image` / `file`) joined to their message, newest first by id; Links are the web addresses in text messages (`lower(body) LIKE '%http%'`, then `formatting.find_links`, the SAME rule `linkify` uses, so the tab lists exactly what shows as a link), with the preview's title when `link_previews.url` matches; their pages go by message seq. `PAGE` (48) a page, "Show older" for more. Each item has "Show in chat" (`/chats/<id>?before=<seq+20>#m-<id>`, like search). Not live: the page shows what was there when it opened. Demo (`seed.sample_media`): a cup mockup in Papel Studio, Mika's final logo in Ana's DM, Ben's trail map in his, Carlo's palette notes (a file) in his; Weekend Hike has its Wikipedia link and Launch Plans its checklist file.
- **Stories (PR #5; `stories.py`, `views/stories.py`, `static/stories.js`, migration 0008).** A story is a photo (`files.prepare`: WebP, no EXIF, must be a picture; optional caption) or a text card (words, max 250, on one of `BACKGROUNDS`: pink, purple, blue, teal, orange, night; white text at 4.5:1 or more) that ends 24 hours after it is posted (`expires_at`). Tables: `stories` (image/thumb deferred), `story_views` (UNIQUE story+viewer: Seen by counts a person once), `story_reactions` (UNIQUE story+user: the same emoji again takes it back, another replaces it; `tools.EMOJI` only), `close_friends`, `story_mutes`, and `messages.story_id` + `is_story_reply` (a private reply). **Who may see (`can_view`, the one place):** not expired, and the owner, or one of the owner's `presence.contacts` (people who share an active chat, blocks removed both ways, so demo and real people never meet) and, for `audience == "close"`, on the owner's Close Friends list. Anything else is 404 (`load_visible` raises `NotFound`), pictures included (`/stories/<id>/image`, `/thumb`, served by `views/files.respond`). Seen by and reactions are shown only to the owner. Muting (`story_mutes`, only people you chat with) hides someone from your circles and the Stories page; it doesn't change who may see. At most `MAX_LIVE` (10) live stories each (`TooMany`). Expired stories never show (every query filters `expires_at > now`) and are deleted by `stories.purge`: on each new story, on Try Demo, and by `flask purge-stories`. **Replies** go through `chats.start_dm` + `chats.send_message(..., story_id=)`, so every chat rule (blocks included) still applies; `tools.prepare` adds `m.story_info` (`stories.quote_info`: the story's card or thumbnail while it lasts, then "Story expired"; the story id is SET NULL when the story is purged, and `is_story_reply` remembers it was one). **Pages:** the circles above the chat list (`_story_tray.html` in `_chat_list_pane.html`; you first, then people with an unseen story, then the rest, newest first; `.ring.is-new` in the app's colour, `.is-seen` grey), `/stories` (yours with "N seen", then everyone's), `/stories/new`, the viewer `/stories/<person id>?story=<id>` (starts at the first unseen; marks seen; Previous/Next are links over the left third and right two thirds, and after the last story it goes on to the next person in the circles' order), Settings > Privacy has Close Friends and Muted Stories (`views/settings.extras`). **Live:** `story.new` / `story.gone` go to the audience (and the owner's other tabs): `stories.js` swaps in `/stories/tray` (the circles, an HTML fragment); `story.seen {story_id, count}` and `story.reacted {story_id, user_id, name, emoji}` go only to the owner (the counts update; a toast on the story pages). The viewer's 5-second timer (`stories.js`, with the CSS bar) pauses while you type a reply, open Seen by or a menu, hold a finger down, or the tab is hidden; arrow keys and Escape work. **Demo (`seed.sample_stories`):** Ana's photo (unseen), Ben's card (seen: grey ring), Carlo's Close Friends card (Mika is on his list) with his private reply in their DM, Dana's (muted by Mika), and Mika's own seen by four with Ben's heart; Mika's Close Friends are Ana and Ben. The crew (`stories.after_post_hooks` -> `crew.story_posted`): when the visitor posts, Ana (or the first teammate who may see it and isn't played by a real person) opens it 4 s later and reacts 2 s after, so Seen by changes live.
- **Messages are toasts** (`_toasts.html`, bottom right): `flash(msg)` is good news and fades after 6 seconds; `flash(msg, "error")` stays until closed. Scripts can make one with `toast(text, error)` (`app.js`).
- **Settings holds the controls, and the menus only navigate.** Settings has PAGES (PR #4, the owner's "organized" request): Account (`/settings`: name, password, recovery code, time zone), Appearance (colour, light or dark), Notifications, Privacy (show when online, blocked people) and Devices (install, log out others, log out), with Settings' own small menu (`.settings-nav`: a column on wide screens, wrapping pills under 64rem). There is ONE way into Settings: the profile menu. Each form comes back to its own page (`ACTION_PAGES`); sections other modules add are placed by `SECTION_PAGES`. Light or dark is saved per device in `localStorage` (`theme.js` applies it before the page draws).
- **The menus (the owner's layout, PR #3):** on a computer the sky has only the logo, the Demo tag, **Chats** (with the unread number) and **Stories** (PR #5); your picture at the bottom opens the **profile menu** (`_account_menu.html`: who you are, the demo note, Settings, Invite a friend in a demo, Log out). There are no New Chat, Search or Settings entries in the menu: **New Chat and Search open inside the chat page**, from the two buttons above the chat list (`_chat_list_pane.html`), in the right-hand panel where a chat would be (`_chat_panel.html`; `/chats/new` and `/search` keep their addresses). **On a phone (under 56rem) there is no sidebar and no header:** a bar at the BOTTOM (`.bottom-nav`) has Chats (with the unread number), Stories and Profile (your picture, opening the same profile menu upwards). Inside an open chat, New Chat or Search the bar steps aside (`.has-open`) and the back arrow returns to the list. Both unread badges carry `data-total-unread` (`chat.js` updates all of them).
- **No decorative emoji.** Icons are the line SVGs in `_icons.html`.
- **Page titles are bare:** `page_head(title)` from `_macros.html`, with no line of text under the title.
- **Title Case** for the menu, page titles (`h1`), section headings, tabs, empty-state titles and anything that names a page. Small words (a, an, the, and, or, of, in, on, to, for, with, as, at, by) stay lowercase unless first. **Sentence case** for everything else: action buttons ("Create account", "Log out others"), labels, hints, messages. The main button of a page is last on the right.
- Controls are the same height (`--control-height`) with bottoms aligned. Sizes in `rem`; the root font steps up at 1600 / 1920 / 2300px. Tabs are pills that wrap, never a sideways scroll.
- The sky sidebar shows from 56rem up; below that, the bottom bar instead (see "The menus").
- The pages before you log in (`_welcome.html`) are one centred column on a soft day sky: the logo, the name, the tagline, then the card; the login has "Forgot password?" beside the Password label, a full-width Log in button, "New here? Create an account.", and the demo card under an "or" line.
